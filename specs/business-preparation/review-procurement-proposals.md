## Product outcome, users and scope

An active business owner turns selected offers in their saved supplier shortlist into a quotation-request or purchase/cart proposal, reviews its exact server-derived seller, source, items, quantities and known or unknown estimated amounts, explicitly approves the current proposal revision, then separately requests its simulation. The two action types remain distinguishable. A proposal is creator-private and accessible only to its creator while they remain an active owner of the participation's business. This F09 owner-only restriction is narrower than F10 r2's general "active business member" wording and matches the current F10 service's active-owner check; it does not grant additional roles. The approved shared sandbox service owns immutable proposal revisions, actor-bound approvals, cancellation, simulated execution receipts and audit. This story adds the Phase 4 business-facing create/revise/review/history workflow; it does not duplicate that service's approval or execution rules.

Approval and simulation are separate explicit user actions; the UI shows an approved-but-not-yet-simulated state. A quotation-request draft is not a supplier quotation. No seller is contacted. Real orders, bookings, payments, organiser email execution, proposal deletion and public reconciliation are excluded. A simulated receipt is never presented as a real quote, order or successful external action.

## Use cases and user interface

From supplier research at `/business/supplier-research`, the active business owner follows an additive link to the separate business-only `/business/procurement-proposals` route. The link is shown only after the current participation context is validated; unsaved shortlist changes use the existing supplier-research leave confirmation before navigation. The new route accepts exactly one strict UUID `participationId` query value, encoded with `URLSearchParams`; duplicate or invalid values show an unavailable state. Before showing labels, an empty state, proposal rows or a create form, the UI successfully reads the authorized supplier shortlist at `/api/v1/business/participations/{participationId}/supplier-shortlist` and confirms its `participationId` matches. The URL is not authority; server responses authorize every operation. Do not trust or interpolate other query values.

The owner chooses quotation request or purchase/cart and selects saved shortlist entries. After validating the current participation's shortlist response, resolve each unique saved `snapshotId` through the authorized `GET /api/v1/business/supplier-research/{snapshotId}` interface in [compare-suppliers v1 / specification revision 5](./compare-suppliers.md). Confirm the returned snapshot ID and `participationId` match the shortlist reference and route, validate the snapshot and find exactly one offer with the referenced `offerId`; use that offer's source-backed fields for the selection display. Deduplicate snapshot reads, retain only the fields needed for selection, and do not keep the full snapshot response or show another participation's data. If shortlist response validation fails, keep proposal rows hidden until context validation succeeds. If the shortlist context is valid but a snapshot detail or referenced offer is missing, fails, or is malformed, discard partial selection data and show unavailable—not an empty shortlist—with all create controls disabled; keep the already authorized current-participation proposal history usable. The empty state is used only when the validated shortlist has no saved references. Every resolved saved entry remains individually selectable, including an entry whose price is unknown; the UI does not prefilter on client-clock freshness. One proposal may include offers from exactly one snapshot: after an offer is selected, entries from other snapshots remain visible but disabled with an accessible explanation until the current selection is cleared. The UI does not automatically split selections or send mixed-snapshot requests. The owner may create separate proposals manually after reviewing each selection. Within the selected snapshot, F10 remains authoritative and rejects a mixed seller/source, stale, deleted, unsafe or inconsistent selection. A rejection preserves state, reloads canonical data and asks the owner to review. The F09-US03 slice owns the new supplier-research entry link; existing F09-US02 tests remain protected and unchanged, with this link covered by the new F09-US03 acceptance tests.

The owner can enter a quotation recipient and request text only for a quotation request; recipient details are explicitly labelled unverified and are never sent. After creation, the owner reviews the saved revision's source-derived, unverified seller, source URL and retrieval time, item descriptions, quantities, known estimated subtotals or fixed unknown reasons, a complete total when available, and the fact that shipping, taxes and availability may be unknown before approval. The UI does not present `listedPrice` as an estimate or use it in calculations. The F10 `sources[]` evidence is rendered as inert text; no provider identity or supplier trust is implied.

The owner can reopen proposals for the current participation, create a new immutable revision when details change, inspect server-provided approval expiry and historical receipts, cancel before an execution claim, and explicitly approve and simulate the exact current revision. The F10 list endpoint is creator-wide; the UI paginates it with `limit=100`, filters to the validated current participation, immediately discards non-current rows without retaining their quote data, and never displays the creator-wide total or other participation's proposals. A successful load requires consistent `total`, `limit` and expected `offset` values, unique proposal IDs, and every page; if the list changes during pagination, restart once. A page failure, access denial, inconsistent or duplicate page, or more than 100 pages causes all partial data to be discarded and a generic unavailable state with all mutations disabled. A valid owner with no proposals for the participation sees an empty list only after all pages load and filter successfully. Once approval succeeds, show its approver, revision and expiry and require a separate explicit simulation action; do not treat approval alone as execution. Approval expires fifteen minutes after the server records it; the server is authoritative for expiry and allows first execution only while `now < expiresAt`. At first execution, the service rechecks current creator/business authority, same approving actor, latest proposal revision, server-computed payload digest, and source freshness. A previous unclaimed approval becomes unusable after a new proposal revision. An expired or stale result shows that no receipt was created and offers reload/review, never silent reapproval. If a claim already committed, an authorized replay returns its same receipt without repeating simulation. Inaccessible resources do not disclose proposal, approval or receipt details.

The UI enables controls only for a validated canonical current revision, according to this state matrix:

| Canonical current state | Revise | Approve | Simulate | Cancel |
| --- | --- | --- | --- | --- |
| `open`, no valid approval for the current revision/digest | Enabled | Enabled | Disabled | Enabled |
| `open`, at least one valid approval for the current revision/digest | Enabled | Disabled | Enabled for the latest valid approval | Enabled |
| `open`, all matching approvals are expired | Enabled | Enabled | Disabled | Enabled |
| `open` with malformed current non-amount proposal or approval data | Disabled | Disabled | Disabled | Disabled |
| `open` with malformed current amount data only and valid proposal ID/revision | Disabled | Disabled | Disabled | Enabled |
| `open` with invalid proposal ID/revision metadata | Disabled | Disabled | Disabled | Disabled |
| `open` with a persisted indeterminate-execute marker for this revision | Enabled | Disabled | Disabled | Enabled |
| `cancelled`, `simulated`, `failed` or `uncertain` | Disabled | Disabled | Disabled | Disabled |
| Historical revision | View only | Disabled | Disabled | Disabled |
| Any proposal mutation in flight | Disabled | Disabled | Disabled | Disabled |

An approval is usable only when its server `state` is `valid`, its proposal revision and digest match the validated current revision, and `approvedBy` is the current creator. If one or more approvals qualify, use the latest by the canonical `(approvedAt, approvalId)` ascending response order; F10 currently returns approvals in this order. An approval response must match the displayed revision and digest before Simulate becomes available. A mismatched approval is malformed current data, not an expired approval. Expiry and authorization remain server decisions; the client clock is never authority.

Before dispatching Execute, persist a minimal localStorage marker containing only `actorId`, `proposalId` and `proposalRevision`; do not store the idempotency key or proposal/quotation content. Strictly validate the marker when reading it and synchronize marker changes across tabs. A marker suppresses Simulate across tabs and reloads for that revision. If storage cannot be read/written or the marker is malformed, fail closed and do not send Execute. Treat network timeout/abort, an unparsable or malformed 2xx response, HTTP 500/internal error, and unknown execute status/code as an indeterminate transport result: retain the marker, reload canonical detail, and do not retry. A valid returned receipt clears the marker and is displayed as terminal. A recognized response documented by F10 as non-committing (including `revision_conflict`, `stale_source`, `expired`, `cancelled`, `idempotency_conflict`, `validation_error`, `quota_exceeded` or `service_unavailable`) is not an indeterminate result and is never automatically repeated: reload and validate canonical detail. Clear the marker only if that detail confirms no receipt and a non-terminal state; then allow only controls justified by canonical state and an explicit new user intent. Stale-source/revision conflicts require refreshing/reviewing the source and creating a new revision first. If reload fails, is inconsistent, or returns a claimed/terminal state without a valid receipt, retain the marker and fail closed. Unknown codes, including any response that may indicate an execution claim, retain the marker. Other tabs reload canonical detail after observing a marker clear and before re-enabling controls. A persisted marker with an open revision keeps Approve/Simulate disabled until a confirmed non-receipt clears it or a new immutable revision is created and explicitly reviewed. Clear markers on logout, actor change, a canonical receipt, a newer revision, or a confirmed definitive non-receipt with no receipt; they contain no PII. F10 server idempotency remains the backstop for concurrent tabs and any marker loss.

After a create timeout, reload the proposal list before a user may start another create; F10 create has no idempotency key, so the UI never repeats it automatically. After a timeout or invalid response for revise, approve or cancel, reload canonical detail and disable all proposal mutations until that reload succeeds. Any returned `failed` or `uncertain` receipt is terminal, with no retry or reconciliation control. Each explicit new simulation intent receives a fresh UUID idempotency key; no mutation is automatically repeated.

Show progress, validation/stale-source/conflict errors, cancellation, and terminal failed/uncertain outcomes without claiming success. After any conflict or indeterminate result, reload and display canonical server state rather than claiming an outcome or automatically repeating a mutation. Keep the existing shortlist and saved proposal history usable after every error. Provide clear loading, empty, error and completion states, keyboard operation, labelled controls, focus management after mutations/errors, semantic item tables, approval confirmation semantics and responsive layout; status and error meaning must be announced in text and not conveyed by color alone. Verify keyboard-only operation, accessible names, announced status/errors, and reflow without horizontal scrolling at 320 CSS pixels and 1280 CSS pixels.

Show known source-backed item estimates in SGD, with integer minor units rendered as two decimal places. Never render an unknown price/subtotal as zero or silently add it as zero. Show a complete proposal total only when every item's server-derived subtotal is known. When at least one but not all line subtotals are known, show a clearly labelled "Known-items subtotal" for known lines only, and state the number of unknown line items (not units). Both the complete total and partial subtotal are presentation-only sums of validated server-derived per-item subtotal strings. For F09 response validation, known amounts must be canonical non-negative base-10 integer strings from 0 through 999999999999999999 minor units in SGD; zero is valid, and leading zeroes are not canonical except for "0". Unknown amounts are null with a server-owned reason. A known amount requires currency `SGD` and no unknown reason; an unknown amount requires null currency and one of `source_price_unknown`, `quantity_mismatch` or `arithmetic_overflow`. Any other amount/currency/reason combination is contradictory. Use arbitrary-precision integer or decimal-string arithmetic: at the F10 r2 maximum of 100 items and 999999999999999999 minor units each, the aggregate may reach 99999999999999999900 minor units. Do not use fixed-width overflow, floating-point rounding, exponent notation or loss of precision. For this F09 workflow, use an explicit `SGD` code prefix, en-SG grouping and exactly two fractional digits, without converting through an imprecise numeric type; this choice is pinned here rather than inferred from inconsistent existing supplier-research formatting. For example, the maximum line amount is `SGD 9,999,999,999,999,999.99` and the maximum aggregate is `SGD 999,999,999,999,999,999.00`. These aggregates are presentation-only, are not persisted, and are never sent as authority or included in a proposal payload/digest. Never label a partial value as the proposal total. A known zero is displayed as known SGD 0.00 and remains distinct from an unknown amount. When no line subtotal is known, show no numeric subtotal and state that all item prices are unknown. If a response contains a missing, malformed or contradictory amount, currency or unknown-reason value, show a data error for that revision, withhold its monetary rows and aggregates, and preserve saved state; do not substitute zero or count invalid data as a valid unknown. Other valid revisions remain accessible. For a malformed current revision, keep Cancel available only when its proposal ID and current revision metadata are valid; the server still enforces current authority and expected revision. Disable revise/approve/execute until a valid canonical current revision is reloaded. If identity/revision metadata is also invalid, disable all mutations for that proposal. A malformed historical revision does not hide a separate valid revision or its receipt state. Apply the same labels and revision-bound values in current and historical proposal views and any receipt context that presents item estimates; the receipt outcome itself remains service-provided. A quotation-request recipient is marked unverified and all entered recipient/request text remains private simulation data, not an email destination. Match the F10-US03 r2 server-enforced bounds exactly: one syntactically valid email address of at most 254 characters with no CR/LF, and trimmed request text of at most 1,000 Unicode code points; reject either field for a purchase/cart proposal. Client validation may improve feedback but does not replace server validation. Rejected input leaves saved proposal revisions and the shortlist unchanged. Both optional quotation fields are in the exact server-bound payload and digest, so changing either requires a new immutable revision and approval. Render all source and user text as inert escaped text.

## Inputs, outputs and functional contract

The UI consumes the business-owned supplier snapshot and shortlist interfaces and the approved [F10-US03 business sandbox approval contract revision 2](../shared/approve-external-actions.md). Create requests contain `participationId`, `actionType`, `shortlistId`, `expectedShortlistRevision`, selected `{snapshotId, offerId, quantity}` items, and optional `recipientEmail`/`requestText` only for quotation requests. Revision requests also contain `expectedProposalRevision`; approval sends only `{proposalRevision}`; cancellation sends only `{expectedProposalRevision}`; execution identifies the selected `approvalId` in the route and sends only `{idempotencyKey}`. No request contains a client-authoritative seller, source, price, subtotal, aggregate or payload digest. The service derives and validates those values and binds approval to its computed digest.

The implemented proposal payload contains `seller: {supplierName, sourceOrigin: {scheme, host, port}}` and `items[]` with `snapshotId`, `snapshotRevision`, `offerId`, `quantity`, `supplierName`, `productDescription`, `listedPrice`, `estimatedItemSubtotalMinorUnits`, `estimatedCurrency`, `unknownReason` and `sources[]`. Each source entry contains `sourceId`, `requestedUrl`, `finalUrl`, `retrievedAt` and `sourceRevision`. Quotation payloads additionally contain `recipientEmail` and `requestText`. `listedPrice` is captured source metadata; the UI does not render it as an estimate or use it in calculations. Only a validated `estimatedItemSubtotalMinorUnits` and its paired `estimatedCurrency`/`unknownReason` may drive a displayed line estimate or aggregate. Seller names and source values are unverified external content, rendered inertly. The F10 r2 prose does not enumerate all nested payload fields; this F09 consumer mapping follows the current implementation without changing F10.

The proposal list response is `{items, total, limit, offset}`; each item is the current implementation's `ProposalView`, also returned by detail. A view has `proposalId`, `proposalRevision`, `creatorId`, `businessId`, `participationId`, `actionType`, `mode`, `recipientVerification`, `payload`, `shortlistId`, `shortlistRevision`, `payloadDigest`, `state`, `createdAt`, `updatedAt`, current-revision `approvals[]`, current-revision `executionReceipt|null`, and `revisions[]`. Each history entry contains `proposalRevision`, `actionType`, `payload`, `shortlistId`, `shortlistRevision`, `payloadDigest`, `state`, `createdAt`, `updatedAt`, `approvals[]` and `executionReceipt|null`. The F10 r2 prose promises full immutable revision, approval and receipt history but does not enumerate this DTO shape; Isaac directed F09 to consume the implemented shape without changing F10.

Validate the fields consumed by this UI before rendering: UUID identity fields, including equality of `proposalId` to the route/detail identity; `mode == "simulation"`; action, proposal, approval and receipt enums; positive integer revisions and quantities within 1..1,000,000; SHA-256 payload digests as 64 lowercase hexadecimal characters; and timezone-bearing ISO-8601 timestamps. `revisions[]` must be non-empty, have unique positive integer revisions, and its maximum revision must equal top-level `proposalRevision`. Top-level current-revision fields (`actionType`, payload, shortlist identifiers/revision, digest, state and timestamps), approvals and receipt must match that highest revision's entry. `creatorId` must match the authenticated actor; `businessId` and `participationId` must match the validated context. Each approval must have a unique UUID, matching revision/digest and `approvedBy == creatorId`; its state is `valid|expired|cancelled|consumed`, `approvedAt` and `expiresAt` are valid timestamps, and the response array follows ascending `(approvedAt, approvalId)` order. An `open` proposal cannot contain a consumed approval; a cancelled proposal cannot contain a valid approval; a terminal proposal must have the matching receipt and consumed approval. Each receipt must have UUID identifiers, a valid UUID idempotency key, matching revision, an approval ID present in that revision's approval history, `actorId == creatorId`, an outcome of `simulated|failed|uncertain`, and valid start/completion timestamps. `reasonCode` is absent/null for `simulated`; for a terminal non-success outcome, treat it as opaque and never render it. `open`/`cancelled` states have no receipt; `simulated`/`failed`/`uncertain` states agree with the receipt outcome. Do not require a replayed receipt's approval ID or idempotency key to equal the latest approval or a just-sent key.

The payload must have exactly one snapshot, one seller and one source origin, with 1–100 unique `(snapshotId, offerId)` items; every item has positive snapshot revision, valid identifiers, bounded quantity, seller identity consistent with the payload, and validated estimate/currency/unknown-reason combinations. `seller.supplierName` and `sourceOrigin.host` are non-empty strings; `sourceOrigin.scheme` is `https`, and its port is an integer from 1 through 65535. Parse each `finalUrl` as a safe absolute HTTPS URL and require its canonical `(scheme, lower-case host, effective port)` origin to match the payload source origin; all final URLs across every item must match that same origin. A mismatch is malformed non-amount data, so no proposal controls are enabled. Quotation recipient fields are allowed only for `quotation_request`; `recipientVerification == "unverified"` iff a valid recipient email is present, otherwise it is null, and quotation request text is present only for that action type. Validate each source entry's UUID, positive source revision, requested/final URL and retrieval timestamp before inert display; allow only safe HTTPS URLs and never fetch or preview them. Ignore unknown extra response fields but never render them. A malformed non-amount DTO makes that proposal's controls unavailable; the existing Cancel-only exception applies only to malformed current amount data with valid proposal ID/revision metadata. Top-level approvals and receipt describe only the current revision. Sort history by numeric `proposalRevision`; do not rely on response-array order.

The list is creator-wide and paginated. Fetch pages using `limit=100` and expected offsets, with a maximum of 100 pages per load. Require stable `total`, expected `limit`/`offset`, expected page length and unique proposal IDs; recheck the first page after completion to detect a list shift. If a total/order change or duplicate is detected, discard all pages and restart once. A page failure, 401/403/404, malformed response or second inconsistency discards all partial data and shows a fixed unavailable/service-error state with mutations disabled. A total above 10,000 proposals also fails closed without showing partial results. Filter to the validated current `participationId` before retaining rows; immediately discard all other-participation rows and never display the creator-wide total. Do not show other participation proposals in this route.

F10 checks source freshness at creation/revision, approval and first execution; evidence exactly 24 hours old is fresh. First execution is allowed only while server time is strictly before `expiresAt`. Committed-claim replay returns the stored receipt only after current authorization and does not repeat simulation. The service performs a local simulation only: it does not enqueue external work or dispatch an outbox, provider adapter, email, seller request, booking, order or payment, now or later.

Authorization follows Isaac's direction to match current shared guard behavior. [Access-authorised-workspaces revision 5](../shared/access-authorised-workspaces.md) is currently In review (its r4 safe-error amendment was user-approved); it is a role reference, not the sole authority for the business-route Origin order. F10 r2's error list does not itself enumerate 403. For a mutation, missing/untrusted Origin receives 403 before authentication. Otherwise, missing/invalid session receives 401; pending mandatory password change receives 403 `password_change_required`; wrong product role or no active owner membership anywhere receives 403 `forbidden`. An authenticated business owner who remains an active owner elsewhere but lacks active owner membership for the target participation, or targets a missing, other-creator or other-business proposal, receives 404 `not_found`. Revoking the owner's only active business membership yields 403 at the workspace guard; revoking one of several memberships yields 404 for the affected participation. The current product model has only the business `owner` membership role. A valid active owner with no proposals for the current participation receives a 200 empty list after all list pages load successfully. Fixed UI messages distinguish only "not permitted" (403) from "unavailable" (404); never render server `detail` or claim which role, membership or Origin check failed.

Map only a recognized code with its expected HTTP status to a fixed UI message/action: `unauthenticated`/401 prompts sign-in and clears private proposal/quotation UI state; `forbidden` or `password_change_required`/403 shows "Not permitted" and clears private state; `not_found`/404 shows "Unavailable" and clears the affected private view; `validation_error`/422 says the saved selection or entered fields cannot be accepted; `revision_conflict`, `stale_source`, `expired`, `cancelled`, `execution_claimed` or `idempotency_conflict`/409 says the proposal changed and must be reloaded/reviewed; `quota_exceeded`/429 says the service limit was reached and to try later; `service_unavailable`/503 says the service is temporarily unavailable and requires reload; `internal_error`/500, `method_not_allowed`/405, unknown codes/statuses, code/status mismatches, missing code and non-JSON error bodies say the request could not be completed and require reload. For an execute result that could have committed without a valid receipt, apply the indeterminate-marker rule above. Never render/log `detail`, `title`, `instance` or raw response bodies. Private responses, including failures, are no-store; all mutations require authenticated session and trusted-Origin protections.

Quotation recipient and request text never appear in URLs, local/session storage, console output or telemetry, are never rendered as `mailto:` links, and are cleared from UI memory on logout, actor/participation/route change, unmount, back-forward-cache restore, or 401/403. The only browser-persisted data is the minimal no-retry marker specified above; it contains no quote PII. After filtering the creator-wide list, discard rows from other participations immediately and never log them; retain only the current-participation rows in memory. Do not enable browser autocomplete/spellcheck on private quote fields. No proposal field is sent to a model or provider. Minimal audit records may be written for denied/conflicting operations, but contain no private payload or recipient text; rejection tests assert preservation of shortlist, proposal, approval and receipt state, not absence of permitted audit rows.

## Constraints, security and non-functional requirements

RD01, RD07; SEC01-03, SEC06-07, SEC09-12. Approval binds exact payload and actor; stale, expired or changed details invalidate it. Uncertain outcomes are shown as terminal; reload canonical state, but do not retry or expose reconciliation controls. Error text is mapped from allowlisted codes; private quote text is not persisted or logged. No model/provider, seller contact or external effect exists in this workflow. See [accepted decisions](../../docs/project.md#accepted-review-decisions) and [security rules](../../docs/security.md). Accessibility checks include keyboard-only operation, accessible names, announced status/errors, and reflow without horizontal scrolling at 320 CSS pixels and 1280 CSS pixels.

## External interfaces and dependencies

Depends on the approved [external-action sandbox service/API v2](../shared/approve-external-actions.md) and the supplier-owned interfaces in [compare-suppliers specification revision 5](./compare-suppliers.md): authorized shortlist reads at `/api/v1/business/participations/{participationId}/supplier-shortlist` and snapshot detail reads at `/api/v1/business/supplier-research/{snapshotId}`. Compare-suppliers is In progress; its r4/r5 text approvals and separate verification status are not upgraded by this dependency. The business UI is a consumer; it must not write the external-action or supplier-owned tables directly. The shared contract's no-external-egress simulation boundary, one-seller/source rule, source freshness, exact price/unknown handling, expiry, cancellation, idempotency, retention, audit and safe error semantics are authoritative. Its validated per-item decimal-string minor-unit subtotals are the only inputs to display-only sums; only values bound to the selected immutable proposal revision may be used. Known server zero amounts remain numeric zero, while unknown, missing or invalid amounts are never substituted with zero or included in a sum. The UI does not recalculate line subtotals from unit prices or quantities, and malformed responses are not shown as numeric estimates. Real commerce, seller contact, real email, provider allowlists and reconciliation remain deferred; changes to that boundary require a new explicit product/security approval rather than implementation inference.
