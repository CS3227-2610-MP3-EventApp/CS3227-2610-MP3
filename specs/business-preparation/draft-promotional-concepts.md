## Product outcome, users and scope

An authenticated business member creates a private, editable promotional concept for an existing participation of their business. The capability uses an AI provider to suggest poster copy, freebie concepts and a layout brief. A user can save, reopen and edit the draft. Event and published setup facts remain distinguishable from generated creative suggestions. The result is a planning draft, not approved marketing, a factual warranty, a print-ready asset or an order.

This capability does not generate images or print-ready exports, research suppliers, send messages, publish content, place orders, spend money, make application decisions or modify accepted event/setup records. Image generation/export quality and supplier/procurement behavior need separate approved contracts.

Approved Phase 1 scope: the authenticated business owner who currently owns the participation may create concepts for any extant participation status (`draft`, `submitted`, `accepted` or `rejected`); acceptance is not required. Each concept and job is private to its creator. Saved concepts remain until that creator deletes them; job records and uncommitted generated artifacts expire 30 days after creation. Local deletion makes no claim about provider-side copies. Use only current event facts and explicitly published setup facts. Unpublished setup drafts, application/contact/review data and other businesses' data are excluded. Future business-member roles remain outside this contract.

## Use cases and user interface

The user selects one of their business's participations, reviews which event/setup facts are available to use, and submits a request for concepts. The EventParticipation must still exist and belong to the requesting business. It has no lifecycle status; associated Submission status (`draft`, `submitted`, `accepted` or `rejected`) does not gate eligibility. Before generation, the interface explains which selected facts and user-entered brief will be sent to the configured AI provider; Generate is the explicit request and acknowledgement. The user-entered brief is not automatically scrubbed and may itself contain personal or sensitive information, so the interface must advise users to include only details needed for the concept. The system excludes contact details, account names/IDs, application decisions, private organiser notes and unselected business records from server-sourced context.

The result presents three clearly separated areas: editable poster-copy suggestions, editable freebie concepts, and an editable layout brief. The interface shows current authoritative facts separately, with their source and revision, and allows the user to insert only those facts as structured fact elements. It labels AI-generated and subsequently user-edited prose as unverified creative text that must be checked before use. The model cannot author a verified fact element. A fact element is rendered from its current authorised source record; an unknown or stale fact is unavailable or visibly marked unknown, never filled in by the model.

Users can save, reopen, edit and delete their private concept. Editing or deletion requires current authority and the current draft revision. Empty history, missing published setup, stale source facts, active/failed/cancelled generation, provider unavailability, quota exhaustion and access loss have clear feedback. Manual editing remains available when generation fails. No generated result is called approved or publish-ready.

## Inputs, outputs and functional contract

Inputs are an existing business participation selected by the user, a bounded creative brief, and an explicit selection of permitted event/setup facts to include as structured fact elements. All IDs and authority are resolved by the server; client-supplied identifiers do not establish membership or ownership. The Phase 1 API/DTO contract below is agreed for this capability; its additive job envelope and lifecycle are defined by shared AI task contract revision 5.


**Version 1 interface:** all paths use `/api/v1`, camelCase JSON, UUID identifiers, positive integer revisions, no-store private responses, trusted Origin on mutations, and current server-side authorization.

| Method/path | Request/response |
| --- | --- |
| POST `/business/participations/{participationId}/promotional-concepts` | `{requestId,expectedEventRevision,expectedSetupRevision,brief,factFields,dataSharingConfirmed:true}`; `expectedSetupRevision` is null when no setup is published; returns 202 `BusinessPromotionalConceptJob v1`. Each successful job creates and persists a new concept; it never replaces an existing concept. |
| GET `/business/participations/{participationId}/promotional-concepts` | Owner-only paginated `{items,total,limit,offset,latestJob}`; `limit` default 20, maximum 100, `offset` >= 0 |
| GET `/business/promotional-concepts/{conceptId}` | Current authorized owner; canonical concept |
| PUT `/business/promotional-concepts/{conceptId}` | `{expectedRevision,posterCopySuggestions,freebieConcepts,layoutBrief}`; replaces creative fields only, preserves server-owned fact provenance, and increments revision once |
| POST `/business/promotional-concepts/{conceptId}/refresh-facts` | `{expectedRevision,expectedEventRevision,expectedSetupRevision,factFields}`; atomically replaces the selected fact fields with current server-read values and revisions, incrementing revision once |
| DELETE `/business/promotional-concepts/{conceptId}?expectedRevision={revision}` | Deletes the saved concept; returns 204. Generation jobs always create new concepts and are never bound to a deleted concept, so cannot recreate it. |
| GET/POST cancel `/ai/jobs/{jobId}` | Shared job service; F09 envelope and creator-only access use the additive shared contract revision 5 |

Request deduplication uses a UUID `requestId`, scoped to requesting user and promotional workflow: an identical replay returns the original job, while reuse with a different payload returns 409 `request_conflict`; replay does not consume a second job quota. Failure codes are `cancelled`, `timed_out`, `quota_exceeded`, `provider_unavailable`, `invalid_output`, `source_changed`, and `access_revoked`; HTTP failures use 401 `unauthenticated`, 403 `forbidden`, indistinguishable 404 `not_found` for private foreign resources, 409 `revision_conflict`/`source_changed`/`request_conflict`/`active_job`, 422 `validation_error`, 429 `quota_exceeded`, 503 `service_unavailable`, or 500 `internal_error`. Unknown request fields are rejected. Permission checks precede private source/conflict details. Limits are: `brief` trimmed 1-2000 Unicode code points; generation returns 1–5 poster-copy strings of 1–4000 code points each, 1–10 freebie concepts (each `name` 1–120 and `description` 1–500 code points), and `layoutBrief` 1–4000 code points. Saved edits may contain 0–5 poster-copy strings, 0–10 freebie concepts and an empty layout brief, so users can remove unwanted suggestions. All strings are plain text, reject control characters beyond normal whitespace, and are rendered without HTML or automatic links. `factFields` is a unique selection from `event.title`, `event.startsAt`, `event.endsAt`, `event.timezone`, `setup.boothLabel`, and `setup.setupInstructions`; the server resolves values and revisions. If no setup is published, `expectedSetupRevision:null` is required and no `setup.*` field can be selected. A missing/unpublished selected field returns 422 `validation_error`; a source revision mismatch returns 409 `source_changed`. Provider output contains only the three creative fields above; it cannot add facts, source references, URLs, prices, actions or extra fields. The server associates selected fact fields with the draft and renders them separately.

`PromotionalConcept v1`: `{id,participationId,revision,sourceRevisions:{event,setup},factFields,sourceFacts:[{field,value,observedRevision,currentRevision,status}],posterCopySuggestions,freebieConcepts,layoutBrief,createdAt,updatedAt}`. `sourceFacts` contains selected permitted fields only. Its status is `current`, `stale` or `unavailable`; for `current`, value and currentRevision match observedRevision; for `stale`, include the latest value/currentRevision only while the source remains currently readable and published, while observedRevision records the concept-bound source revision; for `unavailable`, value and currentRevision are null and no former value is returned. `BusinessPromotionalConceptJob v1`: `{id,eventId,participationId,state,createdAt,updatedAt,completedAt,failureCode,providerMayHaveRun,concept}`. A successful job persists a new concept before returning it; failure never creates or replaces a concept. The promotional workflow uses the same owner-scoped counters and provider gate as business preparation. Limits: 10 jobs/user/UTC day, one active job, 60-second provider timeout, 180-second overall deadline, 40,000 outbound code points, 4,000 output tokens, 40,000 response-content characters, at most two simultaneous provider calls per worker, shared 30/minute provider gate, one bounded HTTP 502/503 retry, and 30-day local job/artifact retention. These are the approved shared business limits.
A saved concept is an owner-private, versioned draft bound to its requesting user, business participation, source references/revisions, and creation/update times. Each successful generation creates a separate saved concept. The user edits and reopens generated concepts; manual blank-concept creation is outside scope. Generation never silently edits an existing concept. It contains editable poster-copy suggestions, freebie concepts, a layout brief, and zero or more structured fact elements. Reopening returns the saved revision and its source/freshness status. A successful edit advances the revision once. A stale expected revision returns a conflict without overwriting the saved draft. A successful delete permanently removes that concept from local reads; generation is not bound to a concept and always creates a new concept only on successful completion. A retained completed job returns `concept:null` after its result is deleted; reading the old job never recreates the concept. Generation failure, cancellation, timeout, quota rejection or invalid model output does not replace an earlier saved revision. Save/edit/delete operations do not change event, setup, application, budget or procurement records.

**Provider output contract:** strict JSON with separate `posterCopySuggestions`, `freebieConcepts`, and `layoutBrief` fields, plus no model-authored factual fields, URLs, actions, prices or recipient data. Event/setup fact elements are selected and rendered by the server from an allowlist of current authoritative fields, not copied from model prose. Schema and fact-reference equality prove only shape and traceability; they do not prove the semantics of natural-language creative text. Therefore no creative prose is displayed as verified fact. Unknown fact references or malformed/extra output fields fail closed and are not presented as validated output. These bounds are the versioned v1 contract.

Generation binds the event/setup revisions and selected fields at request time; source changes before dispatch or final commit fail the job with `source_changed`, without saving a concept. On later reads, current source revisions determine `current` versus `stale`. Stale values are returned only if currently readable and published, and then contain the latest authorized value/revision while retaining the original observed revision. If setup is unpublished or the owner loses authority to read a source, its previous value is suppressed and status is `unavailable`. Creative fields remain accessible to the concept creator while their access to the concept remains active. Fact refresh is explicit through the refresh-facts endpoint; stale writes fail with 409 unless the current source revisions are supplied. Event/setup source reads and writes serialize by their current producer contracts.

## Constraints, security and non-functional requirements

Accepted [RD01 and RD07](../../docs/project.md#accepted-review-decisions) and [SEC01-04, SEC06, SEC08, SEC10-12](../../docs/security.md) apply. In particular:

- Every protected read, edit, delete, generation request, job read/cancel and worker dispatch/commit checks current server identity, business authority, participation scope and draft/job ownership. Role labels or client IDs never grant access. Denial leaves saved drafts and business records unchanged.
- Prompt text, event/setup text and provider output are untrusted data. They cannot alter instructions, authority or provider/tool scope. The workflow exposes no arbitrary database, browser, shell, purchase, publication or messaging tools.
- Only the user-entered brief and selected permitted event/setup values may leave the server. Exclude contacts, account/business names and identifiers, applications/reviews, private setup drafts, unrelated records and secrets from server-sourced context. The user's brief may contain personal data; disclose this, request minimum necessary input, and do not claim automated scrubbing or anonymisation. Logs contain no prompt, generated content, credentials or unnecessary personal data.
- Strict schema checks, source-reference checks and current-source checks precede persistence/display. These checks do not establish semantic truth of free text. Generated and user-edited prose remains visibly unverified creative suggestion; only structured server-rendered fact elements are represented as sourced facts. Users must review prose before using it.
- Provider, model availability, outbound-data disclosure/consent, provider retention, local retention, deletion behavior, request/output bounds, timeouts, quotas, retry rules and access scope must be agreed before Ready. F09 adopts the approved shared business provider/data/environment controls and limits recorded in this revision and revision 5 of the shared job contract.
- Provider failure, cancellation, rate/usage limits, invalid output preserve prior saved drafts and leave manual editing available to a still-authorized owner. Access revocation prevents further private reads or edits, while any in-flight generation is prevented from committing. No claim is made that local deletion removes provider-side copies.
- Live development/test use follows the approved synthetic-only or explicit real-data opt-in/event-allowlist path above. Production provider calls remain disabled; project deployment and development/production separation release gates still apply.
