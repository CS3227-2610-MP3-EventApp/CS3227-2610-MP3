## Product outcome, users and scope

An authenticated attendee can save private event preferences, bookmark published activities, maintain one manual draft per event, and explicitly accept a valid version. The owner alone can access this planning state. F02 owns domain persistence and deterministic validation and works without any AI provider, worker, job or artifact. It provides a foundation for the later attendee AI workflow but does not satisfy the role LLM gate. Shopping, reservations, travel estimates, recurring break scheduling, AI generation and notifications are excluded. Existing programme/authentication implementations are consumed without changing their approved behavior. SDD/protected baseline, privacy/security, real persistence and online/separate-environment evidence apply; LLM/provider tests are N/A for this manual slice.

## Use cases and user interface

From a published event, the attendee can bookmark an activity independently of adding it to the draft; see/remove bookmarks; edit preferences; and add/remove unique activities in a chronological draft. The draft shows current item, room/venue, event-local times, exact SGD cost and accessibility notes, with unknown accessibility explicitly unknown. Overlap and insufficient user minimum-gap warnings do not prevent draft saving, but block acceptance. The attendee sees every blocking reason before explicitly accepting a plan. Saving preferences or a draft never replaces an accepted plan. Prior accepted versions remain identifiable until owner deletion. Empty, loading, failed, stale/conflicting and retry states are understandable; forms and controls are keyboard accessible. No UI role selection or supplied owner ID establishes authorization.

## Inputs, outputs and functional contract

### Approved scope and value semantics

Preferences are optional plain-text interests (soft), optional hard SGD budget ceiling, private plain-text accessibility needs and a user-set minimum gap in minutes defaulting to zero. Monetary values use integer SGD cents, never binary fractional money. Null budget means no ceiling; zero means only free selected activities. Total cost sums each unique selected activity's current price once. There are no quantities or shopping costs. Activity intervals are half-open: exact adjacency is allowed when the minimum gap is zero. Positive minimum gap applies between consecutive chronological activities; no inferred walking time or recurring-break rule is introduced.

If trimmed accessibility needs are nonempty, every selected activity requires explicit owner suitability confirmation for those needs and that item's published revision. Confirmation is the attendee's acknowledgement after reviewing available facts; it is not a producer/provider claim, accessibility certification or conversion of unknown information into verified evidence. Unknown remains visibly unknown after confirmation. No confirmation or a stale confirmation blocks acceptance. Confirmations bind to both the preference revision and programme item revision; a preference revision change invalidates prior confirmations, including when accessibility needs change. Confirmations never satisfy overlap, cost or gap rules. An approved clarification of AC04 below is recorded to make this distinction explicit.

Technical request bounds: interests at most 1000 Unicode code points; accessibility needs at most 2000; budget null or integer 0 through 2147483647 cents; minimum gap integer 0 through 1440 minutes; at most 500 unique activities per draft. Reject over-bound values rather than truncating. Strings are plain text, trimmed, with empty strings represented as empty. These are validation limits for the bounded manual interface, not inferred policy for future AI prompts.

### PlanningState v1 shape and freshness

All JSON keys are camelCase. UUID resource IDs are opaque strings. Server resolves the attendee from the session. `GET /api/v1/attendee/events/{eventId}/planning` returns `{eventId, stateRevision, preferences, bookmarks, draft, acceptedVersions, currentAcceptedVersionId}`. `preferences` is `{revision, interests, budgetMinorUnits, currency, accessibilityNeeds, minimumGapMinutes}`; currency is always `SGD`. `bookmarks` is an array of unique published item IDs. `draft` is `{revision, preferenceRevision, items, validation}`. Each draft item is `{programmeItemId, observedProgrammeRevision, accessibilityConfirmed}` plus `currentItem` containing the canonical PublishedProgramme v1 item detail (the same event/item/venue/room facts used by attendee browsing), `currentProgrammeRevision`, and `changed` boolean. `acceptedVersions` contains safe owner-only version summaries `{id, version, acceptedAt}`; full versions are read through the route below. `validation` is `{valid, totalMinorUnits, currency, issues}`; each issue is `{code, itemIds}` with safe display text supplied by the client allowlist.

Never-created state reads as `stateRevision: 0`, preference/draft revision zero, empty bookmarks/items/history, null current pointer and unsaved default preferences. GET causes no domain writes. Every successful effective mutation increases `stateRevision`; preference or draft revisions increase only when the corresponding content changes. Draft `preferenceRevision` is the preference revision observed when the draft was last saved. No-op commands return current state without incrementing revisions. Chronological ordering uses current start instant, end instant, then stable item ID. Display uses event timezone. Facts resolve from the programme producer, never client-supplied price/time/location. Distinct item IDs prevent duplicate charging.

### Commands, CAS and errors

Every mutation body includes `expectedStateRevision`; zero is an explicit create-if-never-created precondition; previously deleted empty state uses its retained tombstone revision. The server serializes per owner/event so commands with a stale revision return conflict without writes. Successful commands return the complete current PlanningState v1, except deletion returns 204.

| Command | Body beyond expectedStateRevision | Observable behavior |
| --- | --- | --- |
| `PUT /api/v1/attendee/events/{eventId}/planning/preferences` | `{interests, budgetMinorUnits, currency, accessibilityNeeds, minimumGapMinutes}` | Replace preferences; invalidate previous-revision confirmations; retain accepted history |
| `PUT /api/v1/attendee/events/{eventId}/planning/bookmarks/{itemId}` | None | Add a same-event published item once; idempotent when already present |
| `DELETE /api/v1/attendee/events/{eventId}/planning/bookmarks/{itemId}` | None | Remove bookmark only; absent removal is an idempotent no-op |
| `PUT /api/v1/attendee/events/{eventId}/planning/draft` | `{expectedPreferenceRevision, items: [{programmeItemId, observedProgrammeRevision, accessibilityConfirmed}]}` | Replace the one draft; malformed/duplicate/foreign/unpublished references rejected; conflicting schedules save with warnings |
| `POST /api/v1/attendee/events/{eventId}/planning/accept` | `{expectedDraftRevision, expectedPreferenceRevision}` | Atomically validate current facts/revisions/constraints, create immutable accepted version and set current pointer |
| `GET /api/v1/attendee/events/{eventId}/planning/accepted/{versionId}` | None | Owner-only accepted snapshot plus current facts/change indicators |
| `DELETE /api/v1/attendee/events/{eventId}/planning` | None | Owner deletes preferences, bookmarks, draft, accepted versions and current pointer for this event atomically |

For DELETE commands, the JSON body carries expectedStateRevision as for other mutation commands. Acceptance retains the draft. Repeated acceptance of the same draft revision with the same checked preference/programme revisions returns its existing accepted version without duplicate history, including an uncertain-response retry, provided current authority and facts still validate. This exact duplicate check precedes stale-state rejection only when the request matches the current draft, current preferences and current item revisions. The duplicate response is read-only and never moves currentAcceptedVersionId backward; mismatched or superseded draft/preference/item revisions return 409. A new draft revision permits a new accepted version. An empty draft returns 409 constraint_violation with empty_itinerary and preserves state; this validation rule is included in the exact revision approved by Yik Bing. An accepted detail is `{id, eventId, version, draftRevision, preferenceRevision, acceptedAt, preferencesSnapshot, totalMinorUnits, currency, items, needsAttention}`. Each accepted item is `{programmeItemId, observedProgrammeRevision, accessibilityConfirmed, acceptedItem, currentItem, changed}`; acceptedItem is the immutable canonical PublishedProgramme v1 item detail checked at acceptance and currentItem is that same canonical detail resolved now (nullable only when a later supported producer lifecycle makes the item unavailable). preferencesSnapshot has the same preference value fields as the current preferences object. needsAttention is true when current facts or applicable constraints differ from those accepted. Snapshots are immutable until owner deletion. Source resources are never rewritten. Deletion does not delete account, event or programme records. A content-free audit can retain action/resource/outcome/time, but never private planning payloads. No automatic expiry is introduced; the owner can delete their event planning records, after which GET returns the empty state. Explicit deletion is the exception to retention of accepted history and the future F05 keep-cancelled-entry rule.

Errors use safe RFC-style problem responses with stable `code` and allowlisted field errors: 401 unauthenticated, 403 wrong role or required password replacement, 404 missing/foreign/unpublished event or activity and inaccessible accepted version, 422 invalid shape/bounds/currency/duplicates, 409 `stale_revision`, `stale_programme` or `constraint_violation`, and 503 unavailable storage. For 409 the owner may receive current state plus structured validation issues; never another owner's state. Every rejected/failed write preserves all domain planning state, except permitted minimal audit entries. Mutations enforce trusted Origin; reads are no-store. Atomic transactions prevent acceptance/deletion partial state. A content-free monotonic owner/event revision tombstone prevents a deleted state from reusing an old stateRevision on recreation. After deletion, GET returns empty content with the current monotonic stateRevision rather than zero; zero applies only to never-created planning state. No old revision becomes valid after delete/recreate.

## Constraints, security and non-functional requirements

Apply RD03/RD04/RD07 and SEC01/02/05/10/11; use existing cookie session/role/Origin enforcement. Organisers, businesses and other attendees cannot list/read/write planning state. Direct server requests must test these boundaries. Privacy applies to lists, historical versions, validation/errors and audit data. Accepted plans remain usable while AI is unavailable. Real PostgreSQL write/restart/read and no-partial-state checks are required; fixtures are not persistence evidence. Protected tests and independent behavior/security review are prerequisites under the [agent workflow](../../workflow/agents/README.md). Online delivery with separate development/production data/credentials and human review remain separate completion gates.
