## Product outcome, users and scope

EventApp presents authorised attendee, organiser and business work as a coherent, professional, clean business experience. Users can understand where they are, move between permitted tasks, recognise the primary action and its consequences, and see truthful feedback while information or work is pending. This contract governs shared presentation and interaction across role journeys. Domain specs own permissions, available actions, accepted data, validation, AI jobs, external approvals and mutations; this contract does not grant access or alter those outcomes. Public or signed-out entry points are included only where their domain visibility contract permits them. The bounded [role-entry prototype](preview-role-entry-and-workspaces.md) owns its three-tab entry, registration, synthetic-session and dashboard-preview criteria without claiming real authorisation.

Included: workspace orientation, consistent navigation and terminology, visual hierarchy, responsive reflow, accessible interaction, loading and status feedback, error recovery and preservation of work during navigation or failures. Excluded: prescribing production palette/tokens, component library, page/component tree, animation technique, exact screen designs, domain-specific form fields, authentication policy and domain performance guarantees. The approved prototype visual direction is only a review reference, not a mandate for production choices. This capability supports each role's journey but does not itself satisfy the required LLM feature for any role. Specification-driven delivery, security review and online environment checks follow the shared workflow and project gates.

## Use cases and user interface

An attendee moves from published activities to a private plan; an organiser moves among programme and review work; a business participant moves among applications and preparation. At each destination the interface identifies the current workspace, event or business context where applicable, location within that workspace, and available next actions. Directly opening a permitted destination, refreshing it or returning through browser history preserves this orientation. Role/context switching appears only for contexts returned by the authorised access contract. Similar actions and status types use consistent labels and visual treatment across journeys. Key content and primary actions are readily distinguishable from secondary information; visual styling conveys a restrained, legible business character without relying on colour alone.

On narrow screens and at increased text size, navigation and content reflow so task content, controls and status remain usable without losing meaning or requiring a second interface. Keyboard users can traverse navigation, including a collapsed menu when present, and forms in a meaningful order, identify focus, close temporary navigation and return to the relevant work after a transition. Status changes, validation errors and task outcomes are available to assistive technology without requiring a user to detect animation or colour. Motion, if used, does not block a task, convey the sole status signal or disregard a reduced-motion preference.

During a delayed read or action, the interface shows which view or action is pending and retains enough context to avoid confusing the delay with an empty result. If the wait becomes unusually long under an agreed threshold, it explains that work is still pending and offers only recovery actions supported by the underlying contract. Completion shows a success state only after the authoritative response confirms success. Failures distinguish retryable problems from validation, permission and conflict outcomes when the domain contract permits it. An empty authorised result is distinguishable from loading, denial and failure. A user can revisit the current work after a recoverable failure without silently losing entered data; domain-specific persistence remains governed by its own spec.

## Inputs, outputs and functional contract

Inputs are the server-authorised actor and available contexts (`CurrentActor v1`), the chosen destination and context, user-entered work and display preferences, and domain response categories such as pending, success, empty, validation error, conflict, forbidden, unavailable, cancelled and uncertain external outcome. Client-supplied role or route context is not authority. Domain responses and revisions remain the source of truth for visible status. No shared UI-specific server endpoint or persistent data shape is mandated by this contract.

Outputs are the visible and accessible current location, available navigation destinations, content and action hierarchy, operation state, contextual error or success message, and a recovery route where the domain contract supports one. Switching views must not itself submit a domain action. The interface must not present an unconfirmed mutation, AI draft, external send or stale result as accepted/current. When a domain operation reports a conflict, denial or failure, visible accepted state reflects the authoritative result and the user's recoverable input remains available as allowed by the domain contract. The UI may preserve an unsaved draft locally or by an approved domain draft contract; any promise of cross-session recovery requires the domain's persistence evidence.

## Constraints, security and non-functional requirements

[SEC01 and SEC02](../../docs/security.md) govern access and private-data visibility; hiding a link is never the permission boundary. [SEC03 and SEC09](../../docs/security.md) keep displayed source text and external links untrusted and subject to destination policy. [SEC04, SEC06 and SEC07](../../docs/security.md) govern validated AI results and exact-action approval; pending or optimistic presentation cannot bypass those boundaries. [SEC10 and SEC13](../../docs/security.md) govern failure preservation, AI recovery and stale review evidence. The UI must not reveal another user's private context through navigation labels, status details, errors or cached views after context change or revocation. [RD01–RD07](../../docs/project.md#accepted-review-decisions) remain authoritative, including business-wide membership, frozen submissions, valid-plan acceptance, historical changes, fixed notification recipients and owned AI work.

The following are proposed targets for human review, not accepted policy or verified results. UI-02 proposes WCAG 2.2 AA for shared interaction and presentation. Its review matrix uses an effective content width of 320 CSS pixels, including a 1280 CSS-pixel desktop reference viewport at 100% zoom followed by 400% zoom; keyboard-only use; reduced-motion enabled; and one browser/screen-reader pair selected by the product/accessibility owner before verification. Representative journeys cover attendee, organiser and business participant tasks. The exact browser, screen reader and test device remain for that owner to select.

UI-03 proposes a shared-interface feedback budget, not a domain/API completion or route-load SLA: after a user action starts asynchronous work, an accessible pending indication is visible within 200 ms of the action; if the operation is still pending at 10 seconds from request dispatch, show a neutral “Still in progress” indication. These limits are inclusive. If an authoritative terminal response arrives before or at the 200 ms boundary, show it as soon as received; a pending indication may already have appeared but is not required. Any authoritative response takes precedence over a pending timer and cannot be overwritten by it. Measure elapsed time with a monotonic clock in the production-build UI on a human-selected fixed browser/device; a controlled pending-response fixture and deterministic test clock isolate presentation feedback, with no network shaping or provider/server latency included. Only controls supported by the domain contract may be offered. The owner must select the browser/device setup and approve any broader route-performance scope before such measurements; no online performance result is claimed.

UI-04 proposes that unsaved private input is held in memory only and scoped to the exact authoritative actor and business/event context. It remains recoverable across single-page route changes and recoverable operation failures within that same scope. Passwords, tokens, session material and full registration payloads follow the authentication contract's lifecycle and are never retained under this draft-preservation rule. No persistent browser storage or cross-session recovery is promised. Warn before in-app navigation away from unsaved input and request a browser warning on reload/page close where supported; no warning is guaranteed on forced termination or crash. After reload, restore only a saved domain draft returned by its authoritative API. A user-selected actor or context switch, confirmed logout, confirmed session expiry, or authoritative access loss clears the old private in-memory draft before another scope is shown. During pending or transiently unavailable actor revalidation, conceal private content and retain the old draft in memory; restore it only after authoritative confirmation of the exact same actor and scope, and purge it on confirmed actor/scope mismatch, denial, logout, expiry or revocation. An ambiguous logout response does not by itself establish logout success or failure.

UI-05 proposes distinct visible labels for the producer's response categories: pending (“In progress”), authoritative success (“Completed”), empty (“No results”), validation (“Needs correction”), conflict (“Changed elsewhere”), unauthenticated (“Sign in required”), forbidden (“Access denied”), unavailable (“Temporarily unavailable”), authoritative cancellation (“Cancelled”), and uncertain external outcome (“Outcome not confirmed”). These labels do not change domain meaning. A view departure, elapsed timer, client abort or lost response does not establish success or cancellation. Show only recovery actions supported by the producer contract; an uncertain external outcome must not invite blind retry and may offer reconciliation only when that contract provides it.

Revision 4 feedback requires three parts when an operation fails: the existing distinct category label, a safe specific reason known from the authoritative producer, and a concrete supported next action. Producers own fixed permitted reason codes/details; never render arbitrary exception/Pydantic/database text or reflect request values. Field validation names only fixed permitted fields. When no more specific reason is safe or known, say `The request could not be completed.` and offer a permitted refresh/recovery action. Do not replace useful approved guidance with only a category label. This applies to authentication, application closure/validation/conflicts and decisions. For example: `Needs correction` + `The new password must be different from your current password.` + `Choose a different password.`; `Changed elsewhere` + `Application revision changed.` + `Refresh the latest application before deciding.`; `Needs correction` + `Applications are closed for this event.` + `Keep editing your saved draft or choose an open event.`. Application closure uses that correction category despite HTTP 409; revision/decided conflicts use `Changed elsewhere`.

For an ambiguous or lost write response, show `Outcome not confirmed`, explain that the server result could not be confirmed, and reconcile through the producer's authoritative read before a supported retry. A timer, abort, navigation or failed transport never establishes success, cancellation or rollback. Preserve input only within its allowed actor/scope and conceal/purge private data under AC08. No raw secrets, private contact fields or unrelated entity identifiers belong in reasons.

## External interfaces and dependencies

Consumes `CurrentActor v1` for real available contexts and server denial categories; domain contracts supply resource revisions, action availability, operation outcomes and permitted recovery. Before that producer exists, the bounded prototype may use its documented synthetic role/display-name adapter solely for presentation. In particular, [workspace access](access-authorised-workspaces.md), [role-entry prototype](preview-role-entry-and-workspaces.md), [AI task monitoring](monitor-and-recover-ai-tasks.md) and [external-action approval](approve-external-actions.md) determine their corresponding boundaries. Domain result categories need a consistent user-facing mapping, while exact API names and response schemas remain with each producer. A UI change must tolerate a delayed or stale domain response without treating it as a fresh commitment. Compatibility with delivered domain contracts and preservation of in-progress work must be checked across navigation and deployment; no database migration is specified here.
