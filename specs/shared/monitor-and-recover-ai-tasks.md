## Product outcome, users and scope

An event organiser can request a bounded application-analysis or F05 announcement-draft job, see its status, inspect a validated artifact or actionable failure, cancel work that has not completed, and continue the corresponding manual workflow. Application analysis remains governed by F04-US02; announcement authoring and publication remain governed by F05. The separately approved business extension supports F06-US04 and F09. Infrastructure alone does not satisfy a role's LLM requirement. AI cannot change application decisions, publish announcements, or otherwise change accepted/shared state.

## Revision 7 merge note - 2026-10-23

Both job families share the `ai_jobs` table. `kind` (`application_analysis` | `announcement_draft`, master revision 3) classifies organiser jobs, which all carry `workflow = 'analysis'`. `workflow` (`preparation` | `promotional` | `supplier_research`) classifies business jobs, which keep the default `kind = 'application_analysis'`, carry `business_participation_id`, and never set application, rubric, change or announcement references. The provider rolling-window gate counts organiser, business and attendee-itinerary attempts together. The business criteria first numbered AC08–AC12 in revision 3-B are renumbered AC23–AC27 because master's AC08–AC09 keep their IDs; their wording is unchanged.

## Use cases and user interface

The organiser starts an analysis from a submitted application, sees `pending`, `running`, `completed`, `failed` or `cancelled`, and can open only a report they still have authority to access. Progress is bounded and must not expose prompts or private provider details. Cancellation says whether further processing stopped; a provider request already sent may still consume quota, but its late response cannot be committed after cancellation. Timeout, configuration, rate/quota, malformed-output and worker-interruption failures have safe actionable messages. Manual application review and decision remain available at all times.

## Inputs, outputs and functional contract

The shared job envelope has an explicit `kind`: `application_analysis` or `announcement_draft`. It binds an authenticated organiser, event, owner, request ID, state, timestamps, bounded progress and safe failure category. For `application_analysis`, `applicationId` and rubric references are required and existing submission/comparison provenance remains unchanged; `sourceChangeId` and `announcementDraftId` are null. For `announcement_draft`, `applicationId` and rubric references are null, while `sourceChangeId` identifies the current programme change. `announcementDraftId` is null until successful completion saves the owner's durable draft. These discriminated field rules prevent fabricated application IDs. A completed job exposes only the validated artifact defined by its domain capability. The existing analysis creation/history routes remain unchanged; shared job read/cancel routes continue to address the job ID.

Analysis creation returns `202` with a job ID; `GET /api/v1/ai/jobs/{jobId}` reads job state/result; `POST /api/v1/ai/jobs/{jobId}/cancel` requests cancellation. Durable execution uses PostgreSQL-backed job claims and a separate Python worker. The concrete contract below defines claims, leases and transactions. Workers recheck current organiser role/membership at source, dispatch and commit boundaries. A revoked member's job cannot publish a report; source/rubric versions remain those captured at creation.

## Constraints, security and non-functional requirements

### Concrete organiser job contract

The shared job read response adds `kind`, nullable typed target references, and the existing state/timestamps/failure/dispatch fields without changing application-analysis creation/history routes. Application-analysis results retain their current report envelope and exact `applicationId`/rubric/comparison references. An announcement job has `applicationId: null` and rubric references null, plus real `sourceChangeId` and `announcementDraftId`; the durable private draft is owned by the F05 capability and is not the job report. Only the requesting owner with current event membership can read the job or linked artifact. Foreign/missing job IDs return 404; wrong roles/current membership are rejected by the existing auth boundary. All mutations enforce trusted Origin and reads are no-store. Errors use existing RFC-style problem responses; malformed requests are 422, stale/dedup/active-job conflicts 409, shared daily limit 429, and disabled/missing provider configuration 503.

Request IDs are unique per owner across both job kinds; reusing one for a different kind or target conflicts. Owner active-job and daily quotas count both kinds together, and the global provider-attempt gate remains shared. Creation locks the owner before shared quota/active checks. Worker claims are atomic with a lease bounded by the 180-second job deadline; another worker only recovers expired leases as failed/interrupted, never replays a possibly billed running job. Pending jobs survive restart. Each worker dispatches at most two concurrent calls. Completion, artifact/report insert and content-free success audit commit atomically. Cancellation and completion serialize on the job: first terminal commit wins; repeated cancellation returns current terminal state. Cancelling an in-flight call discards any later result. Revocation detected before a worker boundary ends the job as failed/permission_revoked; no artifact/report commits. Authority is rechecked at dispatch and transactionally at commit; revocation cannot undo a request already dispatched.

The outbound bound counts Unicode code points in the actual serialized system/user message strings, including rubric and framing; oversize input fails without truncation or provider send. The request uses max_tokens 4000 and rejects response content above 40,000 characters before parsing. One retry after two seconds is allowed only for an explicit HTTP 502 or 503, within the overall deadline. HTTP 429, 401/403, other failures, transport exceptions/timeouts and invalid output fail safely without automatic retry. No raw provider body is included in errors/logs.

Dispatch has an explicit database-serialized point: while locking the job and checking current membership/cancellation, record the provider attempt before releasing the transaction for HTTP. Cancellation before this point prevents dispatch; afterwards `providerMayHaveRun: true` explains potential usage even if the HTTP call has not yet left the process. Completion still requires current membership and a non-cancelled job in the final transaction. A shared PostgreSQL dispatch gate caps provider attempts across workers at configured `SOCLAAS_REQUESTS_PER_MINUTE` (default 30, lower than the documented default limit; adjust to the actual key's allowance). Provider 429 fails safely; the app does not claim this local cap overrides provider budgets.

Both workflow kinds require the existing `AI_SYNTHETIC_EVENT_IDS` event allowlist, global synthetic-data opt-in and per-request confirmation. Announcement jobs send only permitted immutable change facts, including authoritative public cancellation reasons; optional editorial change reasons are excluded. They send no attendee, itinerary, application, rubric or credential data. Operators remain responsible for ensuring allowed programme free text contains invented data only. Bounded wording selection and server-rendered facts are defined by the [F05 announcement contract](../programme/draft-and-publish-disruption-announcements.md). The doctor probe always sends fixed invented content. Production provider calls remain disabled.

Terminal jobs and their job-owned reports expire 30 days after creation; explicit cleanup preserves original submissions, decisions, immutable rubric versions and content-free security audit records. For `announcement_draft`, cleanup removes the terminal job but preserves the separately owned private announcement draft and any published announcement. Active jobs are first recovered/failed when overdue. An expired job lookup returns 404. Retention is an application policy and makes no claim about provider-side retention. Production provider calls remain disabled. Synthetic-only live use additionally requires the existing global development/test opt-in and per-request confirmation.

[SEC01, SEC03, SEC04, SEC06, SEC08, SEC10, SEC11, SEC12 and SEC13](../../docs/security.md) apply. The selected provider is SoCLaaS OpenAI-compatible HTTPS `/v1/chat/completions`; live calls are explicitly enabled only for development/test with synthetic data. The provider key is server/worker runtime-only and never enters browser storage, source control or logs. Application-analysis outbound data remains limited to pseudonymous source labels, participant type, description and rubric instructions; it excludes requested space, contact fields, business name, decisions and unrelated records. Announcement outbound data follows its distinct permitted-facts boundary above. Logs omit prompts, source contents, credentials and provider responses.

Plan limits: 60-second provider request timeout; 180-second total job deadline; maximum 40,000 outbound characters and 4,000 requested output tokens; 10 jobs per owner per UTC day; one active job per owner; at most two concurrent provider requests per worker; and at most one retry only for a clearly classified transient failure. Do not retry an ambiguous timeout, authentication/permission failure, explicit budget/quota exhaustion or invalid output. The counter must be enforced atomically under concurrent submissions. No result is displayed before schema, evidence and source-revision validation. Production AI remains disabled pending provider retention/privacy approval and human approval to process real applicant data.

The concrete contract's 30-day cleanup removes terminal jobs and associated reports, preserving submissions, decisions, rubric versions and security audits. An overdue running lease becomes failed/interrupted and is never automatically replayed. Pending jobs remain durable. Explicit new user requests create new jobs within quotas.

`BusinessPromotionalConceptJob v1` is `{id,eventId,participationId,state,createdAt,updatedAt,completedAt,failureCode,providerMayHaveRun,concept}`. It uses the existing five-state lifecycle. `concept` is null until a successful validated concept has been saved; a successful result is the canonical `PromotionalConcept v1` defined in the F09 capability. A new generation always creates a new concept and never replaces an existing one. If the creator later deletes the concept, reading the retained job returns `concept:null`; job reads never recreate or disclose deleted content. Terminal job records and uncommitted generated artifacts expire 30 days after creation; saved concepts are separate records and remain until creator deletion. Cleanup must not delete saved concepts.

The F09 collection/create/detail/edit/refresh-facts/delete endpoints and versioned DTOs are defined in the linked capability. Shared `GET`/cancel `/api/v1/ai/jobs/{jobId}` resolves the stored `promotional` workflow and current requesting owner. Only the creator, who must remain the active owner of the participation's business, can inspect or cancel the job/concept. The EventParticipation must still exist and belong to the current business. Submission status (`draft`, `submitted`, `accepted`, `rejected`) does not affect eligibility; EventParticipation itself has no lifecycle status. Unauthenticated callers receive401, wrong-role/revoked or known-resource outsiders receive403 where appropriate, and foreign/missing private job IDs are indistinguishable404 after role checks. Every mutation checks trusted Origin; responses are `no-store`. Authority is checked on create, list, detail, edit, fact refresh, delete, cancel, dispatch and final commit. Revocation or cancellation before final commit prevents result publication.

Each create request binds `requestId`, participation ID, expected current event revision, nullable expected published-setup revision, selected fact-field allowlist, brief and `dataSharingConfirmed:true`. Request IDs are unique within the requesting user and `promotional` workflow. Replaying the same normalized payload returns the original job without consuming quota again; reusing that ID with a different payload fails409 `request_conflict`. Request/response unknown fields are rejected. Current event/setup values are resolved by the server, never trusted from the client or model. A null setup revision means no setup is published and forbids selecting setup fields. A missing selected field fails422 `validation_error`. Source changes before dispatch or final commit fail the job with `source_changed`, without saving a concept. Fact reads return only currently readable, currently published values; old source values are suppressed when setup is unpublished or the creator loses authority. Stale-but-currently-readable values are labelled stale and contain the current value/revision with the concept's observed revision retained. Refreshing selected fact fields is an explicit owner write with concept revision CAS and current event/setup revisions.

The outbound allowlist contains only the user's brief and selected values for `event.title`, `event.startsAt`, `event.endsAt`, `event.timezone`, `setup.boothLabel` and `setup.setupInstructions`. It excludes account/business/user identifiers and names, contacts, application/submission content, organiser notes, unpublished setup drafts, unselected facts and unrelated business records. The brief can itself contain personal data; the UI discloses its transmission and asks the user to include only needed information. No automated scrubbing, anonymisation or provider-side deletion is claimed. Provider output is strict JSON containing only `posterCopySuggestions` (1–5 strings), `freebieConcepts` (1–10 objects with `name` and `description`) and `layoutBrief`; generated length bounds are defined in the capability. Extra factual fields, source claims, URLs, prices, recipients, tools and actions are rejected.
