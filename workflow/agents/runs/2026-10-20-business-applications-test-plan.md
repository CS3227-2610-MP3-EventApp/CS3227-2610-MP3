## Contracts, setup and limits

Approved scope: one complete exhibitor/vendor application per business/event; active owner membership; explicit assigned-event organiser approval of a known business before opportunity discovery/application; atomic first participation+draft; explicit frozen submission; organiser submitted-only read projection. No global business directory, invitations, approval revoke endpoint, public/open event opportunities, application decision, booth allocation, frontend delivery, AI or external action.

Use only guarded synthetic PostgreSQL at loopback port 5433, account/database `eventapp_test`, distinct from configured development `DATABASE_URL`, with explicit `EVENTAPP_ALLOW_TEST_DB_RESET=true`. Every reset, fixture write and failure trigger calls the existing protected `require_synthetic_reset_target()` first. Root granted this designer exclusive test-DB use for baseline work; no concurrent manual/verifier resets. Never operate on development/production data.

Fixture matrix: two businesses X/Y, active business owners, inactive membership, two events A/B with distinct assigned organisers, an attendee and anonymous client. X can receive approvals for both A/B. Synthetic descriptions/contact markers distinguish private records. Auth identities/sessions are real; event/organiser rows may be inserted as explicit trusted synthetic fixture setup under already-approved authentication storage contracts. Application/approval lifecycle actions use the real FastAPI public routes and PostgreSQL, without replacing auth services, sessions or domain persistence. Fixtures do not prove trusted CLI integration (covered separately by the auth baseline).

Assertions concern public API results and reopened persistent state. Database failure triggers test transaction rollback, not implementation call ordering. No undeveloped application module is imported by fixtures; missing routes can therefore produce meaningful RED after successful real auth setup.
