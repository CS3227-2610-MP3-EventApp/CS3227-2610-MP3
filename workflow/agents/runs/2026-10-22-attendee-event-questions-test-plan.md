## 1. Assumptions to confirm (the specification is silent or ambiguous; the tests encode them)
- **A1 worker seam.** `app.ai.worker.run_once(provider=...)` also claims question jobs and returns `True` when it processed one (including a job that fails at dispatch) and `False` when none is claimable. The tests monkeypatch `worker.sleep` to skip the 502/503 retry wait. The test of cleanup runs `python -m app.ai.worker --cleanup` in a subprocess against the test database.
- **A2 raw model output** is one JSON object and nothing else (no fence, no prose, no second object, at most 40,000 characters). Answered: `{"outcome":"answered","summary":<string|null>,"claims":[{"itemId","itemRevision","field","value"}]}` with 1-20 claims. Unknown: `{"outcome":"unknown","reason":<enum>}`. The model supplies no `itemTitle`, `itemState`, `observedProgrammeRevisions` or any other key (each is an extra key, so `invalid_output`); the server adds them and replaces each claim `value` by the authoritative record value. The `summary` key is always present in answered output in the tests (a missing `summary` key is deliberately not tested).
- **A3 result.** Claims keep the model's order. `observedProgrammeRevisions` of an answered result holds exactly the cited items; of an unknown result it holds every current programme item of the event including cancelled ones and excluding drafts and other events. `itemRevision` is an integer. Datetime `value`s are compared by instant (any offset or `Z`, fractional seconds allowed); naive datetimes, non-ISO text and numbers are invalid. `price` and `capacity` must be JSON integers (`500.0`, `"500"` and `true` for `1` are invalid). `accessibility` is the item-level `accessibilityDetails` (`null` valid only when the record has none). Result `value` of datetime fields is checked by instant, not by string format.
- **A4 request.** Body keys are exactly `requestId` (UUID) and `question` (string); any extra key (`confirmSynthetic`, `ownerId`, `eventId`, `history`, `result`) is 422, as in the F03-US01 precedent. Same `requestId` plus same question replays the existing job with 202 (also after completion) and consumes no quota; same `requestId` with a different question is 409; the `requestId` is per owner (another owner may reuse it). An unknown event in the allow-list is 404; an event whose only item is a draft is 404; ordering of 404 versus 503 for a non-allow-listed non-existent event is not tested.
- **A5 cleaning** removes control (Cc) and format (Cf: zero-width, bidirectional, BOM) characters (they are removed, not replaced by a space), NFC-normalises, collapses whitespace runs and trims, then checks 1-300 code points. The tests only place newline and tab characters next to spaces (newline directly inside a word is not asserted). The job view `question` is the cleaned text and the provider receives the cleaned text.
- **A6 outbound data** is JSON (each non-system message is one JSON document). The cleaned question is exactly one string leaf, appears nowhere else and never in the system prompt. Each activity record (found by the dict that holds the item ID as a value, or is keyed by it) holds, as leaf values, the item's title, type, start and end (as instants), room name, venue name and address, price, capacity, revision, state, accessibility details (when present) and cancellation reason (when cancelled). The event title and time zone appear as leaves. Not sent: event ID, owner ID, job ID, request ID, username, email, display name, any preference, plan, draft, bookmark, accepted itinerary, other attendees' data, other events, unpublished items, and keys `publishedAt`, `lastChangeId`, `cancelledAt`, `maxCapacity`, `eventId` (full list `FORBIDDEN_KEYS` in the test file). Venue and room accessibility details are neither required nor forbidden (ambiguous, see section 6). The outbound request is identical for different owners and planning states. Item order is deterministic.
- **A7 prompt.** One or more `system` messages, constant across questions and events, contain the words "untrusted", "question", "JSON" and "instruction" and none of: the question, programme text, the model name, IDs, the API key. Messages carry only `role` and `content`. The real transport body carries only `model`, `messages`, `max_tokens` (at most 4,000) and `temperature`; a response with `tool_calls`, `function_call` or `finish_reason: length` is `invalid_output`.
- **A8 failure codes** follow the organiser and itinerary slices: `invalid_output`, `input_too_large` or `oversized_input` (with `providerMayHaveRun` false and no provider call), `timeout`/`provider_timeout`/`job_timeout`, and any non-empty code for other provider failures. `providerMayHaveRun` is true after a dispatch and false when the provider was never called. Invalid output is never retried.
- **A9 freshness.** On every read of a completed job, an answered result is stale if any cited item's current revision differs from the recorded one (change or cancellation); an uncited item's change or a newly published item does not make an answered result stale; an unknown result is stale if any item changed (or was cancelled) or a new item was published. A stale view is `{state: "completed", failureCode: null, stale: true, result: null}` with the question still shown. If an item changes between dispatch and validation, the job is either `failed` or stale, and in both cases `result` is null. The value of `stale` on failed or cancelled jobs is only required to be a boolean.
- **A10 storage.** Attendee job tables are found by shape (columns `id, owner_id, event_id, state, request_id`; name not `ai_jobs`); no table or column name of the question workflow is asserted. Cleanup ages are driven by shifting every `timestamptz` column of the chosen rows back 29 or 31 days; deletion of terminal jobs older than 30 days must also remove the stored question text (searched in the row JSON). The migration is a single linear revision after `20261022_0008`; a one-step downgrade and upgrade preserves all listed tables (including the attendee job table) and the itinerary job view.
- **A11 audit.** Audit rows are keyed by `resource_id` = job ID and carry `user_id` = owner and `outcome = success`; a completed job has exactly two (create, complete) and a cancelled job exactly two (create, cancel) with distinct actions. No audit row, anywhere, contains the question text or any answer text. Denied attempts and failed runs are not asserted.
- **A12 UI placement.** The section lives on the attendee event programme view `/attendee/programme/events/:eventId` (the page that lists the event's activities), not on the events list, not on an activity detail page, and not inside My Itinerary. The "Ask again" button resubmits the same question as a new job with a fresh request ID. Cancelling a completed or stale job is not tested.

## 3. UI contract for the developer (event programme view `/attendee/programme/events/:eventId`)
Exact accessible names and copy (case-sensitive, whole-string unless noted):
- Region: `role="region"` named **Ask about this event**, headed by an `h2` with that text; rendered on the event programme view only.
- Textbox: accessible name **Your question**, `maxLength` 300 (a 305-character paste leaves 300), initially empty; a count text **`<n> characters remaining`** (`300 characters remaining`, `288 characters remaining`, `0 characters remaining`); the notice below is the accessible description of the box.
- Notice (visible text): **Your question is sent to an external AI service. Do not enter personal details.** No checkbox in the region.
- Button **Ask question**: disabled while the box is empty or only whitespace, while a request is in flight and while a job is pending or running; next focusable element after the textbox. Activation POSTs `/api/v1/attendee/events/{eventId}/event-questions` with exactly `{requestId: <fresh UUID v4 per explicit ask>, question: <typed text>}`, same-origin credentials; a double click sends one POST.
- Status: one persistent `role="status"` named **Question status** (the same element in every state); idle **No question asked yet.**; during a job it shows the state word (Pending, Running, Completed, Failed, Cancelled; case-insensitive) and, while pending or running, **An answer can take up to a minute.** It polls `GET /api/v1/attendee/ai/question-jobs/{id}` at least every 3 seconds until a terminal state and stops.
- Button **Cancel question**, present only while pending or running; POSTs `.../question-jobs/{id}/cancel`. After a cancelled job the region shows **Question cancelled. You can still browse the programme.** and, only when `providerMayHaveRun` is true, **The AI provider may already have received your question.**; Ask is enabled again.
- Nothing is rendered as an answer unless `state` is `completed`, `stale` is false and `result` is present (no facts, no summary, no unknown message otherwise, whatever else the wire carries).
- Answered: `role="list"` named **Verified facts** with one `listitem` per claim, in order. Each listitem contains the claim's `itemTitle`, **`Revision <n>`**, and one line **`<Label>: <value>`**, plus a link named **`View activity: <itemTitle>`** with `href` `/attendee/programme/events/{eventId}/items/{itemId}`; the exact element text **Cancelled** appears in the listitem only when `itemState` is `cancelled` (a marker, separate from the value). Labels: title **Title**, type **Type**, startsAt **Starts**, endsAt **Ends**, room **Room**, venueName **Venue**, venueAddress **Address**, price **Price**, capacity **Capacity**, accessibility **Accessibility**, state **Status**, cancellationReason **Cancellation reason**. Values: times in the event time zone with 24-hour clock (e.g. `23:30`); price as in the existing programme cards (**Free** or **SGD 12.50**); a null accessibility value as **Not provided**; the other values verbatim.
- After the list: **Only the verified facts are checked against the programme.** The element text **AI summary** followed by the summary text appears only when `summary` is not null.
- Unknown: one message by `reason` and a link named **Browse the programme** with `href` starting `/attendee/programme`, no facts, no summary: `insufficient_evidence` **The programme does not have enough information to answer this question.**; `conflicting_evidence` **The programme has conflicting information about this question.**; `out_of_scope` **This question is outside the programme information available here.**
- Stale (`stale: true`, any `result`): **The programme changed after this answer was prepared, so no answer is shown.** and a button **Ask again** that creates a new job with the same question and a fresh request ID.
- Failed job (any `failureCode`, including timeouts): one `role="alert"` with **The question could not be answered. You can still browse the programme.** and no failure code, provider text or key.
- Creation errors, one `role="alert"` each, no raw detail, no polling: 429 **Daily question limit reached. Try again tomorrow or browse the programme.**; 409 **A question is already being answered. Wait for it to finish or cancel it.**; 503 **Event questions are not available for this event. You can still browse the programme.**; 404 **This event has no published programme to ask about. You can still browse the programme.** The activity links of the programme view stay usable in every state.
- All model and programme text is rendered as text (no `dangerouslySetInnerHTML`, no `href` built from model text); the only anchors in the region are the internal links above.

## 6. Questions for the orchestrator and specification ambiguities found
1. **UI placement (A12).** The spec says "the attendee event view" without a route. The tests use the event programme view (`/attendee/programme/events/:eventId`). If the section should be inside My Itinerary, change `eventRoute` and the two UI02 routes in the fixture/test via a test-change request.
2. **Raw model schema (A2).** The spec gives the result claim shape but not the raw model output shape. The tests assume the model sends only `itemId, itemRevision, field, value` per claim, an always-present `summary`, and nothing else, and that an extra `itemTitle` or `itemState` from the model is `invalid_output`. Confirm.
3. **Outbound shape (A6).** Tests locate fields by value, not by key name, and forbid a set of key names including `eventId`. Confirm that the event ID is not sent, and decide whether venue and room accessibility details (not in the list: "accessibility details" may mean the item's only) may be sent; the tests are silent on them.
4. **Extra request keys (A4)** are expected to be 422 (F03-US01 precedent); the spec only says "malformed". `confirmSynthetic` is explicitly removed by the spec.
5. **Value strictness (A3):** naive datetimes, floats and booleans as integers are rejected; claim order is preserved; identical duplicate claims are not tested (only contradictory ones).
6. **Summary rules.** "Markup characters" is read as `<` and `>`; "numeric token" as digit runs that must equal a digit run in a verified claim value or a cited item title; a summary over 300 characters is not tested.
7. **Staleness of an answered result** by an uncited change or a new item is expected to be false (A9); the spec says "if any cited item changed".
8. **Cleaning (A5):** control characters are removed rather than replaced by a space.
9. **Failure codes (A8):** `input_too_large` or `oversized_input` for oversize; timeouts map to one of three codes; every `invalid_output` case sets `providerMayHaveRun` true.
10. **Audit (A11):** exactly two rows per completed or cancelled job. A denied cross-owner attempt may or may not write a row; it is not asserted.
11. **Storage and migration (A10):** the new migration must follow `20261022_0008` linearly and may add only a column (or similar) to the shared job table; existing exact-table-set tests such as `test_business_applications` remain valid only if no table is added; a new table would need the same kind of test-change request as F03-TCR-01.
12. **UI (A12):** "Ask again" resubmits; the cancelled-before-dispatch and cancelled-after-dispatch texts differ only by the provider note; one failure message serves all failure codes including timeouts, so spec line 25's separate cases are collapsed to one plain message that also states browsing remains available.
13. **Specification status label:** the file header still says Draft and "exact text pending review"; reconcile before freezing.
14. **Spec ambiguity: `cancellationReason` claim on a published item** (value must be null?) is not tested for acceptance, only for rejection of invented reasons; and "link to the programme item" has no target route in the spec (the tests require the existing item detail route).
