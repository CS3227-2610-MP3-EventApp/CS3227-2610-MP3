## Context and test boundary

The backend has organiser application routes, frozen submitted content, event membership authorization and a guarded PostgreSQL acceptance-test harness. These new acceptance cases cover the still-unimplemented AI job, rubric, report and provider behavior through the API and injectable worker seam. Automated cases use a controllable fake provider and invented records. For a live probe, synthetic means realistic fabricated application content with no real applicant, contact or business data. The SoCLaaS key stays outside the repository and ordinary tests make no network call. Dylan believes synthetic live evidence satisfies the course demonstration; lecturer confirmation remains pending.

The planned feature creates an evidence-based report only. It must not create or change an application decision, expose reports to applicants/business users, or allow model output to invoke application tools. Provider schema conformance does not establish factual correctness; application validation must at least prove criterion coverage, source identity/revision, and exact evidence presence under the finally approved normalization rules.

Executable route, rubric, request, job, report, provenance, error, quota, cancellation, retry, retention and live-provider gates are now stated in the two r2 Drafts. The scenario matrix maps stable AC IDs to observable API/database outcomes. `backend/tests/test_ai_analysis.py` is a new pre-implementation suite; its first run is expected to be red while implementation is absent. It has not been independently reviewed or frozen.

## Remaining evidence and approval gates

The r2 Drafts now specify the executable wire/default choices that earlier versions of this plan listed as open: UUID idempotency and tuple replay, 10 accepted jobs per owner per UTC day (including cancelled/failed; retries/replays do not debit again), dispatch and completion/cancellation/revocation serialization, exact rubric/report/job schemas, exact quote checks, Unicode NFKC token/Jaccard duplicate selection with the >=0.50 cutoff and stable UUID tie-break, 30-day job/report cleanup, request/output bounds, 502/503-only retry, and the synthetic event/live gates. The cases should test these choices as Draft behavior without claiming a protected baseline.

Still pending outside this executable fake-provider suite:

1. Independent adequacy review and human approval of the exact r2 Draft contracts; no approval or baseline freeze is implied by this artifact.
2. The course/product owner must confirm that a live SoCLaaS request using invented application records with no real applicant, contact, or business data satisfies the assignment evidence requirement. Dylan believes it does; lecturer confirmation is pending.
3. An accessible SoCLaaS model probe, provider retention/privacy review, and human approval to process real applicant data remain release gates. Production provider calls remain disabled until resolved.
4. Fake-provider tests do not establish model quality, semantic correctness, real provider behavior, provider retention, or live quota behavior. Record those separately in the manual live probe evidence.

## Adequacy and execution notes

- Map each finalized acceptance criterion to at least one observable case; include before/after database state assertions for rejected, invalid, stale, cancelled and failed actions.
- Use guarded PostgreSQL integration for transaction, migration, concurrency, restart and persistence claims. FastAPI mocks alone cannot establish them.
- Use deterministic fake-provider barriers/clocks for race, retry and timeout cases. A fake cannot prove provider compatibility, actual SoCLaaS quotas, retention or model quality.
- Independently review assertions and fixtures before baseline creation. The developer must not edit protected acceptance tests, fixtures, runner/configuration, or baseline guard.
- After exact Draft/contract revision approval and independent adequacy review, create executable acceptance tests, run them pre-implementation and record meaningful red/harness failures/deferred cases. Only then freeze a full immutable commit and list every protected path and complete-suite command in the run record.
- Expected output: selected model and exact request path are verified in a separate synthetic live check; no claim of semantic correctness, deployment readiness or real-applicant privacy approval follows from that check.
