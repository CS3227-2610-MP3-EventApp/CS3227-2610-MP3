- Finding: displaying an existing instant through `localTime` drops fractional seconds. Saving only a changed title reconstructs truncated timestamps. At an event start of `2027-01-01T01:00:00.123456Z`, an item starting at that exact permitted boundary is incorrectly treated as starting before the event after reconstruction to `.000Z`. Away from that boundary, a title-only save can silently reschedule the item.
- Required behaviour: F01-AC03/07 and the approved complete-replacement contract preserve valid untouched facts. Revision 6 accepts explicit-offset ISO instants without imposing whole-second precision and includes exact event boundaries. This regression adds no product policy or new timestamp precision limit.
- Classification: implementation defect and missing acceptance coverage, not a reason to weaken an existing expectation. The independent reviewer reported the issue through the orchestrator; adequacy approval and replacement baseline remain the orchestrator's responsibility.
- Additive correction: one mocked-HTTP UI regression seeds an existing draft with six-digit fractional start/end timestamps, sets the event start equal to the draft start, changes only its title, and expects one complete PATCH at revision 1 and the visible returned draft revision 2. The raw request must retain both original timestamp strings exactly. It does not change either datetime control.
- Why raw assertions: JavaScript `Date` and the existing mock storage normalization retain only milliseconds. Comparing parsed dates or mock stored values would miss lost microseconds. The new case asserts captured request JSON before interpreting the response; existing fixture behaviour and other acceptance cases remain unchanged.
