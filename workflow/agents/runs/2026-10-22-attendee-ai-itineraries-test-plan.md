## 1. Assumptions to confirm (the specification leaves these open; the tests encode them)
- **A1 worker seam.** `app.ai.worker.run_once(provider=...)` is the single seam and also claims attendee itinerary jobs (returns `True` when it processed a job, including one that fails at dispatch, `False` when none is claimable). The tests monkeypatch `worker.sleep` to skip the retry wait. If attendee work lives in another module, change `run_worker()` in the test file via a test-change request.
- **A2 provider output.** The model returns one raw JSON object and nothing else.
  - Feasible: `{"outcome":"feasible","items":[{"itemId","itemRevision","startsAt","endsAt","reason"}]}`.
  - Infeasible: `{"outcome":"infeasible","blockingConstraints":[...non-empty...]}`.
  - Unknown keys anywhere, trailing text, markdown, wrong types, empty or oversized (>40,000 chars) output are `invalid_output`. The server adds `sourceLabel`, `constraintResults`, `preferenceRevision` and `observedProgrammeRevisions`; the model never supplies them.
- **A3 failure codes** are shared with the organiser slice: `invalid_output` (malformed, fabricated, contradictory, stale output), `input_too_large` or `oversized_input`, `provider_unavailable`/`provider_rate_limited`/auth failures (any non-empty code is accepted), `timeout`/`provider_timeout`/`job_timeout` for timeouts.
- **A4 request semantics** copy the organiser slice: `confirmSynthetic` must be literally `true` else 422; same `requestId` and same body replays the existing job with 202 (also after completion) and does not consume quota; same `requestId` with a different body is 409; `requestId` is unique per owner, so another owner may reuse it; the daily limit counts every job (including cancelled) per UTC day; `preferenceRevision` must equal the owner's current preference revision else 409 (revision 0 when no planning state exists).
- **A5 result shapes (pinned by Yik Bing 2026-10-22, decision D1).** `constraintResults` = list with exactly one `{constraint, passed}` entry (`passed` a bool, no other keys) for each of `overlap`, `budget`, `accessibility`. `blockingConstraints` = non-empty list of `{constraint, detail}` (`constraint` one of the three, `detail` a non-empty string, no other keys). `observedProgrammeRevisions` = object mapping item ID to revision integer. An infeasible result has exactly the keys `outcome` and `blockingConstraints`. Backend assertions are exact on these shapes (`assert_constraint_results`, `assert_blocking`); the model may not supply `constraintResults` (extra key is `invalid_output`), and model-supplied `blockingConstraints` must use the same `{constraint, detail}` shape with a known constraint name. The UI renders constraint results as a list with the fixed labels in section 3, shows each blocking `detail` verbatim as plain text, and relies on `items[].itemRevision` and `preferenceRevision` (not `observedProgrammeRevisions`) to detect staleness.
- **A6 outbound data.** The programme has no description field, so programme "descriptions" are exercised through the free-text fields that are sent: item title and the accessibility facts. Venue name, venue address, capacity, publication time, the attendee's own user ID, request ID and bookmarks are treated as not listed, hence not sent. No accessibility preference data leaves the server at all, not even a boolean (decision D2): the outbound request must be identical with and without an accessibility requirement, and the server validates accessibility deterministically against item facts. Item-level accessibility facts are programme facts and are sent. Venue name and address stay out; only the room label is sent (confirmed). The outbound message list uses only `system`/`user` roles with `role` and `content` keys; programme text appears only in non-system messages. If the user message is JSON, its keys are checked against a forbidden list.
- **A7 storage.** Attendee job tables are found by shape (columns `id, owner_id, event_id, state, request_id`, name not `ai_jobs`) because their names are not in the contract. The tests assume they reference `users`/`events` so the module-setup `TRUNCATE ... CASCADE` clears them, and `prepare()` additionally truncates them and any `%provider_attempt%` table before each test. Organiser `ai_jobs` must keep exactly its present 17 columns and stay empty during attendee runs.
- **A9 accessibility result.** `constraintResults` has an `accessibility` entry with a bool `passed`; the tests do not pin its value when an included item has unknown accessibility, because the shapes leave no other field for the "flagged, needs confirmation" signal. The observable flag is the existing planner's `accessibility_unconfirmed` issue on the saved draft, which blocks acceptance until confirmed (tested).
- **A8 migration.** The new migration is a single linear revision on top of `20261022_0007` and downgrades/upgrades one step without losing existing rows.

## 3. UI contract for the developer (inside the existing My Itinerary event view, `/attendee/planning/events/:eventId`)
Exact accessible names and copy (case-sensitive, whole-string unless noted):
- Region: `role="region"` named **AI itinerary suggestions**, headed by an `h2` with that text; rendered only on the event view, not on the event chooser.
- Checkbox: **I confirm this event uses only synthetic data** (unchecked initially; stays checked after a job ends).
- Button: **Generate AI itinerary**; disabled until the checkbox is checked and while a job is pending/running or a request is in flight (a double click must send one POST). It is the next focusable element after the checkbox. Activation POSTs `/api/v1/attendee/events/{eventId}/itinerary-generations` with exactly `{requestId: <fresh UUID v4 per explicit action>, preferenceRevision: <planning state preferences.revision>, confirmSynthetic: true}`, same-origin credentials.
- Status: a persistent `role="status"` named **AI itinerary status**; idle text **No AI itinerary requested yet.**; during a job it shows the state word (Pending, Running, Completed, Failed, Cancelled, case-insensitive match, e.g. "Status: Running"). It polls `GET /api/v1/attendee/ai/jobs/{id}` at least every 3 seconds until a terminal state.
- Button: **Cancel AI itinerary**, present only while pending/running; POSTs `/api/v1/attendee/ai/jobs/{id}/cancel`. After cancelling with `providerMayHaveRun: true` the region shows **The AI provider may already have received your request.**
- Feasible result: `role="list"` named **AI suggested activities** in chronological order; each `listitem` contains the current published title, the local time range in the event time zone (e.g. `23:30`), the `reason` verbatim as plain text, and the `sourceLabel` verbatim. The region also shows a `role="list"` named **Constraint results** with exactly one `listitem` per `constraintResults` entry in the received order, textContent exactly `<label>: Passed` or `<label>: Not passed`, labels `overlap` = **No overlapping activities**, `budget` = **Within budget**, `accessibility` = **Accessibility requirements**; and the exact note **Suggestion only. Nothing is saved until you choose Save as draft.** For an item with unknown accessibility the listitem includes **Accessibility information not provided. You will need to confirm suitability before accepting.** (never wording such as "accessible" or "verified"). Never use `dangerouslySetInnerHTML`.
- Button: **Save as draft** (exact), inside the region: one `PUT .../planning/draft` with `{expectedStateRevision: state.stateRevision, expectedPreferenceRevision: state.preferences.revision, items: [{programmeItemId: itemId, observedProgrammeRevision: itemRevision, accessibilityConfirmed: false}, ...]}` in result order; on success the existing "Draft saved" notice; no accept request; the existing **Accept itinerary** button stays the only way to accept. Not rendered (or disabled) when the result is stale or infeasible.
- Stale: when any `items[].itemRevision` differs from the current published revision of that item, or `result.preferenceRevision` differs from the current `preferences.revision`, show exactly **Stale suggestion: your preferences or the programme have changed. Generate a new itinerary.** and do not show the suggestion-only note.
- Infeasible result: text **No feasible itinerary found.**, a `role="list"` named **Blocking constraints** listing each `detail` verbatim, and **You can still plan manually below.** No suggestion list or Save as draft.
- Failed job (any `failureCode`): one `role="alert"` in the region with **AI itinerary generation failed. You can plan manually below.** and no failure code, provider text or key.
- Create errors, one `role="alert"` in the region each, no raw detail: 429 `daily_limit` **Daily AI itinerary limit reached. Try again tomorrow or plan manually.**; 409 `active_job` **An AI itinerary request is already active.**; 409 `revision_conflict` **Your preferences changed. Reload and try again.**; 503 **AI itinerary suggestions are not available for this event.** The existing manual planning controls (Add to draft and others) stay enabled in all failure and cancelled states.

## 6. Human decisions recorded (Yik Bing, 2026-10-22) and remaining uncertainty
- **D1 result shapes pinned** as in A5; backend assertions exact, UI fixtures use the same shapes.
- **D2 no accessibility preference data to the provider**, not even a boolean; the server validates accessibility deterministically against item facts. Tested by outbound-equality with and without a requirement plus the note canary. Venue name/address stay out; only the room label is sent.
- **D3 known limitation, no test:** the server does not verify the model's infeasibility claim, so a model may report `infeasible` when a feasible plan exists. Only malformed infeasible output (no/unknown/odd blocking constraints, attached items) is rejected.
- **D4 break rule:** the existing planner `minimum_gap` check is unchanged and no new assertion is made about breaks; the `break` constraint is not part of `constraintResults`.
- **Still uncertain:** (a) what value `accessibility.passed` takes when an included item has unknown accessibility (A9, not pinned); (b) the worker seam and failure-code assumptions A1/A3; (c) spec status label in the file header still reads Draft/candidate; (d) the attendee table discovery heuristic (A7).
